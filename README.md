## 추가 개선 아이디어

**기능**

---

- [x] [기능] 라우터 ErrorElement 및 에러 바운더리 추가
  - 라우터 ErrorElement와 에러 바운더리를 추가해, 오류 발생 시 UI가 깨지던 문제를 해결하고 안정적인 오류 화면을 표시하도록 개선했습니다.
- [x] [기능]input 입력 디바운싱 적용 (선택)

- [x] [기능]input 입력값 유효성 검사 + (필요하다면) 간단한 테스트
  - 숫자만 입력되도록 유효성 검사를 추가했고, 금액을 더 쉽게 읽을 수 있도록 자동 콤마 포매팅을 적용했습니다. 이 로직은 직접 입력해보는 것보다 테스트로 확인하는 편이 더 빠르고 확실해서 Vitest로 검증했습니다.

    불필요한 당황 요소를 줄이고, 사용자가 다음 행동을 자연스럽게 이어갈 수 있도록 안내하는 목적입니다.

**리팩토링**

- [x] [리팩토링] ContextApi 사용해서 props Drilling 줄이기 - `savingsGoalState`, `savingsProductList`
  - `savingsGoalState`(목표 입력 금액)와 `savingsProductList`(적금 상품 목록)를 전달하기 위해 여러 컴포넌트에서 props를 계속 내려주는 구조가 불편해서, Context API로 묶어 props drilling을 줄였습니다. 필요한 곳에서 바로 상태를 사용할 수 있어 코드 흐름이 더 간단해졌습니다.
- [x] [리팩토링] 상품 목록 컴포넌트 렌더링 최소화

## 고민되는 점

**❓ Context 사용 깊이에 대한 고민**
Context 값을 컴포넌트 트리의 어느 깊이까지 전달해도 괜찮을지 고민됩니다. <br/>
트리가 깊어질수록 다음과 같은 어려움이 생기더라구요

- 어떤 컴포넌트가 어떤 Context 값을 읽는지 추적하기 어려워지고
- 값이 어디서 변경되었는지 디버깅하기가 점점 복잡해짐

<br/>

**❓ Spacing 컴포넌트 활용 방식**
컴포넌트를 리팩토링하다 보니 `<Spacing size={8} />` 같은 간격 전용 컴포넌트가 계속 신경쓰였어요. <br/>

- 저는 `SectionPadding`이라는 컴포넌트를 만들어 간격을 유연하게 조절하도록 구성했는데, 다른 분들은 이런 레이아웃 간격을 어떤 방식으로 관리하시는지 궁금합니다.
- 또는 `Border`를 패딩으로 감싸는 전용 컴포넌트를 만들어 적용하는 방법도 있을 것 같아요

<br/>

**❓ 추천 상품 선택/해제 UX 고민**

추천 상품 목록에서 선택/해제를 허용해야 할지 고민이 됩니다. <br/>
선택을 해제하면 계산 결과가 사라지고 ‘**상품을 선택해주세요**’라는 문구가 뜨는데, 이 과정에서 UI 변화가 다소 급격하게(과하게) 느껴지더라구요 <br/>
생각해본 대안은 다음과 같습니다:

- 계산 결과 영역의 높이를 고정해, 선택 해제 시에도 동일한 공간에서 메시지를 표시하기
- 추천 상품 목록에서는 선택 변경을 허용하지 않도록 제한하기
  이 외에 더 나은 접근 방식이 있을지도 궁금합니다!

<br/>

**❓ 폴더 구조 공유 부탁드립니다**

저는 프로젝트를 **도메인 중심 구조**로 구성했는데, 다른 분들은 어떤 폴더 구조나 디자인 패턴을 사용하셨는지 궁금합니다.

<br/>

## 설계 시 고려한 점 (Key Design Decisions)

1. 유지보수를 위한 도메인 중심 폴더 구조

기능 확장·변경·삭제 시 영향 범위를 최소화하기 위해 도메인 단위로 응집도 있게 구조를 구성했습니다.<Br/>
특정 기능이 불필요해지면 해당 도메인 폴더만 제거하면 되도록 설계했습니다.

2. 재사용성을 고려한 Shared 레이어 분리

도메인과 직접적으로 연관되지 않는 공통 컴포넌트, 타입, 훅 등을 shared 디렉터리로 분리하여 재사용성과 일관성을 높였습니다.

3. 확장 가능한 컴포넌트 구조

컴포넌트를 단일 파일이 아닌 폴더 단위로 구성했습니다. <br/>
이는 추후 Storybook 도입, 스타일 분리, 타입 정의 등을 손쉽게 추가하기 위한 설계입니다.

4. Context API와 Props Drilling의 균형 유지

과한 Context 사용은 데이터 흐름 파악을 어렵게 만들기 때문에, Context는 props drilling을 완화하는 용도로만 제한적으로 사용했습니다.<br/>
컴포넌트 depth가 깊지 않은(약 2단계) 부분은 명확한 데이터 흐름을 위해 props 방식도 유지했습니다.

5. Vitest를 활용한 순수 함수 테스트

유틸리티 함수의 신뢰성을 확보하기 위해 Vitest를 도입했습니다. <br/>
덕분에 함수가 부수 효과 없이 단일 책임 원칙을 잘 지키는지 검증할 수 있었습니다.

<br/>

## 아쉬웠던 점 (Areas for Improvement)

1. 테스트 환경 도입이 늦어진 점

초기 단계에서 테스트를 도입하지 못해, 순수 함수 여부·추상화 적정성·입출력 검증 등을 미리 확인하지 못한 점이 아쉽습니다. <br/>
유효성 검사 및 포매팅 로직을 추가하는 시점에서야 테스트를 도입했는데, <br/>
처음부터 TDD 방식으로 접근했다면 더 견고하고 자신 있는 구조를 만들 수 있었을 것입니다.

2. 디자인 시스템(디자인 토큰) 적용 미흡

시간 제약으로 인해 색상, 간격, 여백 등 디자인 요소를 변수로 분리하지 못했습니다.<br/>
초기 단계에서 디자인 토큰을 정의했더라면 유지보수성과 UI 일관성이 더 높아졌을 것 같습니다.

3. 도메인 로직과 UI 의존성 분리 부족

View와 Logic을 분리하려고 노력했지만,입력값 포맷팅처럼 일부 로직이 여전히 Custom Hook 내부에서 UI 흐름에 의존하고 있습니다. <br/>
핵심 도메인 로직을 순수 함수로 완전히 분리했더라면 테스트 용이성과 재사용성을 더 높일 수 있었을 것이라 아쉽습니다.

4. 비동기 상태(Loading/Error) 처리의 디테일 부족

ErrorBoundary는 적용했으나,단일 API 호출이라는 이유로 로딩/에러 상태의 UX 세부 처리가 부족했습니다. <br/>
로딩 스켈레톤, 재시도 버튼 등 조금 더 일관된 비동기 UI 패턴을 적용하지 못한 점이 아쉽습니다.
